# v2 — local models, and running work on the box that has the resource

Design note, not a plan of record. Written 2026-08-22, while 0.1.19 is three days
from its commercialization gate. **Nothing here should be built before that gate
closes** — every item touches `policy.mjs`, `limits.mjs`, `ledger.mjs` or
`run.mjs`, and each one re-invalidates phases 01 through 05. This file exists so
the constraints are captured while they are fresh, not so the work starts today.

Companion to `COMMERCIALIZATION_GATE.md`, which is about shipping what already
exists.

---

## The two asks

1. **Dispatch subagents to a local model** via Ollama, so work that does not need
   a paid frontier model stops spending subscription quota.
2. **Use both machines** — a Linux VPS and an Apple Silicon Mac with more
   capable local hardware — so a dispatch can run where the resource actually
   is, rather than where the orchestrator happens to be sitting.

They sound like one feature. They are two, they have different blockers, and the
second is much larger than it looks.

---

## What already exists, precisely

Being accurate about the baseline is most of the work here.

**The agentic harness for local models is already solved, and not by us.** The
Codex CLI takes `--oss --local-provider ollama -m <model>`. That yields a real
agent — tool loop, file edits, sandbox policy, and the same `--json` event stream
`run.mjs` already parses. cmo would not need to learn Ollama's API; it would add
two flags to a command shape it already builds. This removes the objection that
looked fatal ("Ollama is a chat endpoint, not an agent").

**The fleet coordinator is a shared ledger, not a job queue.** `src/server.mjs`
exposes exactly five endpoints:

| Endpoint | Does |
|---|---|
| `GET /v1/health` | liveness |
| `GET /v1/state` | probes, reservations, samples |
| `POST /v1/reserve` | claim headroom |
| `POST /v1/release` | give it back |
| `POST /v1/probe` | publish a meter reading |
| `POST /v1/sample` | publish a measured cost |

There is no endpoint that accepts work, no worker that pulls it, and no path
that returns a result. Every dispatch executes on the machine that decided it.
The fleet shares *accounting* so two boxes do not overspend one subscription —
it does not share *capacity*. Ask 2 is therefore a new subsystem, not a
configuration change.

## Four constraints, in the order they will bite

### 1. The working tree — the one that shapes everything

A cmo subagent edits files. That is load-bearing: the gate doc's whole
"a wrongly-failed dispatch may still have done the work" recovery procedure
depends on agents mutating the tree as they go.

A Mac executing a dispatch on behalf of the VPS **has no repo**. Options are
sync the tree (slow, conflict-prone, and two agents editing two copies is the
double-application failure we already hit once), mount it (a network filesystem
in the path of every file write, on a laptop that closes), or ship a patch back
(only works if the agent's output is a diff, which an agentic loop's is not).

The honest resolution is not to solve it. It is to notice that dispatches come in
two kinds:

- **Repo-bound** — `implement`, `mechanical` edits, anything with
  `needsRepoWrite`. These must run where the files are. Not portable. Ever.
- **Portable** — `judge`, `review`, `research`, `synthesis` over content supplied
  in the prompt. These need a model and a prompt, and nothing else. They return
  text.

Only portable dispatches can cross machines. That is a real limit, and it is also
most of the value, for the reason in constraint 3.

### 2. Capacity is not quota

`providerState()` reads `percentUsed` against a window that resets. Reservations
subtract measured points from that window. The entire ledger speaks *quota*.

A local model has no window. Its scarce resource is one GPU and its memory —
a **concurrency limit**, not a consumption limit. Model it as a percentage and it
reads 0% forever, the headroom rule prefers it for everything, and sixteen
concurrent dispatches all "fit" while the Mac swaps itself to death.

So `ledger.mjs` needs a second reservation kind: **N slots, held and released, no
window, no reset, no decay.** Today it cannot express "capacity" at all. This is
the largest single piece of work in v2 and the one most likely to be
underestimated, because superficially it looks like "add a third key to the
probes object."

Slot count is a per-node config value, not something to infer. One 14B on a
32 GB Mac is roughly two concurrent agents; one 70B is one, if that. Check the
box before choosing:

```bash
system_profiler SPHardwareDataType | grep Memory   # unified memory available
ollama ps                                          # what is resident right now
```

### 3. Three lineages make independence *stronger*, and the code assumes two

`otherProvider()` assumes exactly two providers, and `independentOf` is validated
against the literal pair `codex | claude` in `policy.mjs`. With three, "the other
vendor" stops being a function and becomes a ranking: *any provider except the
one that produced the artifact, best-available first*.

That is worth doing for its own sake, not just to accommodate local. The
README's argument is that a grader sharing the producer's blind spots is not
independent. A local Qwen or Llama grading Claude's output is a **third
lineage** — different weights, different training data, different house style —
and is arguably more independent than Codex is. Adding it strengthens the core
product claim rather than diluting it.

Note where this lands: the most valuable cross-machine dispatch is a *judge*, and
a judge is portable. Constraint 1 and constraint 3 point at the same place.

### 4. The fleet token would start granting code execution

Today `CMO_FLEET_TOKEN` authorizes mutations to an accounting ledger. The worst a
stolen token does is corrupt your headroom numbers.

Add remote execution and the same token authorizes **running an agent with
`--sandbox workspace-write` on another machine**. That is a different class of
credential and must not inherit the current one's handling. At minimum: separate
tokens for accounting and execution, execution off by default, an explicit
per-node opt-in to accept work, and the accepted role set pinned to the portable
list rather than "whatever was asked."

This is the same shape as the embed-key exposure that has bitten this stack
before. Treat a shared secret that reaches a shell as a shell credential.

## The design, in one pass

**A third provider, `local`.** Not a fourth tier under `codex`. A tier would lie
in the receipts (`provider: "codex"` for work Codex never saw) and, worse, would
reserve and consume Codex headroom that was never spent — corrupting the meter,
which is the product's core input. It must be its own provider or nothing.

**Executed through the Codex CLI**, with `--oss --local-provider ollama -m <model>`.
`BINARIES.local = 'codex'`; only the argv differs. The JSON stream, the last-message
file, and the timeout/watchdog path are all reused as-is.

**Config, exactly like the others** — `models.local.{fast,balanced,frontier}`,
plus `local.slots` and `local.endpoint`. Never hardcode model IDs; a local model
list is even more machine-specific than a Codex plan's.

**Routing.** Local is a *floor*, not a peer. Prefer it when
`weight < 0.30` **and** the role is in the cheap set, or when `independentOf`
rules out both paid vendors. Never for `architecture`. Never as a silent
substitute for a frontier model — a receipt that says `local` where the caller
expected `opus` is the same "indistinguishable degradation" failure the
degraded-review label exists to prevent, so it needs the same treatment: label
it, and tell the agent about its own handicap.

**Cross-machine execution** — the genuinely new subsystem:

```
POST /v1/offer      a node advertises: provider=local, models=[…], slots=2
POST /v1/submit     an orchestrator queues a PORTABLE dispatch (role-checked)
GET  /v1/claim      a worker long-polls for work it advertised capacity for
POST /v1/result     the worker returns text + usage, keyed by dispatch id
```

The lease machinery already exists — reservations carry a pid and expire when the
holder dies, which is exactly the property a remote worker needs when the Mac
closes its lid mid-judge. Reuse it rather than inventing a second liveness model.

**What v2 explicitly does not do:** move repo-bound work across machines, sync
working trees, or run the orchestrator anywhere but Claude Code. A dispatch that
touches files runs on the box that holds them, full stop.

## The experiment that comes first, and could kill it

Twenty minutes on the Mac, before a line of cmo changes:

```bash
codex exec --oss --local-provider ollama -m <model> --skip-git-repo-check --cd /tmp \
  "Create fizzbuzz.js with a function fizzBuzz(n), then read it back and tell me what it does."
```

The question is not whether the model writes good code. It is **whether a local
model can hold a multi-turn tool loop to completion.** Small models routinely
fall out of the harness: they emit a tool call, misread the result, and either
loop or stop with the work half done. If a mid-size local model cannot finish a
trivial write-then-read task end to end, then local is not a floor tier, it is a
liability that fails in the most expensive way — silently, having half-edited
something.

Run it at two sizes. Note whether the run terminates, whether the file exists
afterwards, and how long it took against the ~10s a `fast` cloud dispatch takes
today. A local agent that is correct but four times slower is still worth it for
mechanical work; one that is unreliable is worth nothing at any speed.

**Second experiment, if the first passes:** the same thing as a judge, with no
file access — score two candidate paragraphs against a rubric and return JSON.
That is the portable path, and it is the one that actually crosses machines.

## Sequencing

1. Close the 0.1.19 gate. Ship.
2. Run both experiments. If the tool loop does not hold, stop here and write down
   why, so it is not re-litigated in three months.
3. Local as a same-machine provider only — provider `local`, slot reservations,
   floor-tier routing, three-way independence. No fleet changes. This is
   shippable on its own and delivers the quota saving.
4. Cross-machine execution — offer/submit/claim/result, the execution token, the
   portable-role allowlist. Only after 3 has run in anger for a while.

Doing 4 before 3 is the tempting mistake: the fleet story is the interesting one,
and it is worthless if a local agent cannot complete a task on the machine it is
already sitting on.

## Open questions

- **Where does the model list come from?** `doctor` cross-checks Codex model IDs
  against its cache. The equivalent for local is `ollama list`, which means
  `doctor` grows a dependency on a service that may not be running. Warn, never
  fail.
- **What does a cost sample mean with no meter?** Local spends no quota, so
  `recordSample` has nothing to measure. Wall-clock per slot is the closest
  analogue, and it is a different unit — do not overload the same field.
  (Related: `recordSample` is currently Codex-only, so Claude already has this
  bug. Fix that first; it is one line and it is in the gate's finding list.)
- **Does a local dispatch appear in `cmo limits`?** It must appear *somewhere* —
  invisible concurrency is how the Mac ends up thrashing with no explanation —
  but it is not headroom. Probably its own line: `local  2/2 slots busy`.
- **How is a portable dispatch's prompt bounded?** Cross-machine judging means
  shipping candidate text over the network to another box. Fine on a tailnet
  between two machines you own; needs saying out loud before anyone points this
  at a third party's node.

## How this relates to DSPY Relay

Relay (`dspygroup.com/relay`, source in `group-project/orchestrator`) is a control
plane for a distributed AI engineering team: approved worker nodes on
participants' machines receive scoped jobs, work in isolated Git branches, open
PRs, and submit evidence, with humans reviewing and attribution recorded.

cmo is not adjacent to that product. It is the execution substrate underneath it,
and it is the part that already exists. Of Relay's eight stated moat items, cmo
ships **provider-neutral routing** and **cross-model review** today, gate-tested,
plus part of **capacity modeling**. The `offer/submit/claim/result` sketch above
is a minimal worker protocol arrived at independently from the same constraints.

Three consequences, and the first one is a correction to this document.

**Relay solves constraint 1, and v2 should adopt its answer.** The claim above
that repo-bound work can never cross machines assumes the unit of work is a
mutated local tree. Relay's unit is a **branch and a pull request**: the worker
clones, works in a worktree, pushes, opens a PR. Git is the sync mechanism, and
the problem dissolves. A cross-machine dispatch should therefore carry a repo URL
and a branch rather than a `cwd`, and the portable/repo-bound split becomes a
much narrower distinction than section 1 implies. Revisit it before building.

**The ledger does not transfer; the lease machinery does.** cmo scopes one
coordinator per *account pair*, because boxes on different accounts are not
competing for the same window. Relay is twenty participants with twenty account
pairs, so shared-window accounting — most of `limits.mjs` — is meaningless there.
What does transfer is the reservation and lease layer: pid liveness, expiry,
orphan collection, all proven under real contention. Relay needs per-participant
meters that never merge, with capacity as the only pooled quantity.

**cmo is a liability on Relay's open legal question, not a solution to it.** The
pitch states that personal-subscription automation stays disabled pending
provider approval. Driving personal-subscription CLIs is exactly what cmo does.
For one operator on their own machines that is unambiguous; pooling twenty
people's personal subscriptions into a shared queue is the thing provider terms
generally prohibit, and cmo lowers the effort of doing it to nearly zero. Nothing
in this design should be read as progress toward that approval.

Which reframes the local-model half of v2 as the strategically interesting one.
**Local GPU capacity is the only part of a twenty-person pool with no
provider-approval problem**: no credential sharing, no subscription pooling, no
terms question — just idle Apple Silicon doing work. If Relay needs to
demonstrate distributed execution before subscription automation is cleared,
local workers are the unblocked path to it, and the sequencing in this document
(local same-machine first, cross-machine second) is also the order Relay would
want them.
